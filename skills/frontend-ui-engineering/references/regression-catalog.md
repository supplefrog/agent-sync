# Frontend regression catalog

This is a maintained catalog of testing expectations in the existing frontend owner. It preserves the original 75 stable requirement IDs and adds I23/I24 for state-symbol and authored-highlight finishing. It adds no aesthetic ban, feature quota or claim that the full portfolio has passed. Historical complaints, assets, captures and execution results stay in the project evaluation record; this catalog is not their evidence store.

## Select relevant families

Start with the brief, accepted baseline and changed mechanisms. Select `common` expectations for each product, then affected feature families and applicable `workflow` expectations. The coverage checker selects a row when any declared feature tag matches; mechanism-specific conditions therefore use exact tags such as `combined-slide-zoom`, `selection-zoom` and `authored-theme-source`, not generic motion or reader tags. Declare features from the actual DOM/source, chosen behavior and product brief before selecting cases. An author cannot omit a tag to waive a mechanism that exists. Broad tags retained for capability discovery describe alternative fitting contexts; activate an optional capability only when it was actually selected or promised, not merely because a neighboring feature exists. A control with a moving symbol does not thereby need a theme switch; a gallery does not thereby need a zoom. For a repair, select cases that could fail because of that repair and inherited commitments it could disturb.

Feature vocabulary: `animated-selection`, `animated-strip`, `authored-selector-indicator`, `authored-theme-source`, `caret-disclosure`, `chapter-reader`, `combined-slide-zoom`, `common`, `concepts`, `contents-disclosure`, `continuous-disclosure`, `continuous-theme`, `cursor-reveal`, `diagram`, `direct-selection`, `directional-cue`, `disclosure`, `expressive-underline`, `floating-window-zoom`, `form`, `image-zoom`, `masked-gallery`, `native-image-generation`, `passage-textbox-sweep`, `plus-minus`, `reader`, `reader-material`, `resources`, `scroller`, `selection-scroller`, `selection-zoom`, `selector`, `selector-action-row`, `sentence-reveal`, `small-artifact-motion`, `stacked-reader-navigation`, `sun-moon-morph`, `symbol`, `textarea`, `transforming-symbol`, `workflow`.

Classes retain separate authority: `requirement` is explicit; `conditional` checks a defect only when its mechanism/relationship exists; `capability` preserves a wanted option and exercises it where fitting; `tentative` retains a qualified observation without converting it into a verdict; `project` retains task scope rather than global product style. Capabilities are selected for product fit, never quotas. An absent feature is not added to satisfy a row. Brief-specific not-applicable does not clear a missing portfolio case.

Each stable case name is `ID.suffix`, for example `V14.pointer-keyboard`. The suffixes identify decisive scenarios, not browser fixtures or pass receipts. Use real representative content and the actual use position; instantiate the positive task/result and check `nearby_valid` when that distinction could be damaged. Relevant normal, keyboard/touch, long-content, interruption/reversal and reduced-motion paths belong inside those scenarios rather than requiring a universal matrix.

## Evidence methods and acceptance

`browser` observes actual interaction/state and browser facts. `rendered` inspects painted composition, local boundaries and normal-speed/intermediate motion. `source` inspects policy, scope, configuration and execution receipts without pretending those prove UI behavior. `resource` verifies actual discovery, source/demo fit, native asset invocation or supplied-part preview. `human` resolves material scoped taste or tentative optical interpretation after the usable result is viewable. Product-coherence defect readiness uses rendered evidence (`V01`); required human approval of a selected treatment belongs to delivery/integration, not a circular precondition for showing it for taste. Each selected row must cover every method it declares across its case suffixes. The coverage helper records one evidence method per case, so each row supplies at least as many distinct suffixes as methods. Collect separate records when source, interaction and rendered inspection are independently required; source presence cannot stand in for browser or rendered evidence.

Bind real observations to revision/hash, content, viewport, starting state, input and capture method in the existing project acceptance record. The catalog contains expectations only. Mark observed results pass, fail, incomplete or not-applicable with reasons; do not derive a pass from the presence of wording, configured tooling, a synthetic fixture or an exploratory label. Source-only policy receipt acceptance does not establish a related UI outcome.

Coverage asks whether applicable promises, wanted capabilities and valid neighbors were actually exercised. Measurement asks whether collected facts meet declared tolerances. The existing [measurement gate](defect-gate-schema.md) verifies supplied measurements; it cannot establish coverage, optical quality, accessibility certification or natural skill triggering. Keep [defect acceptance](defect-acceptance.md) as the runtime evidence owner and use mature project tests before introducing machinery.

**Full-portfolio status: untested.** No new browser runs or rendered observations were collected for this catalog. A real evaluation portfolio still needs full-content reader cases, distinct concept alternatives, capture forms/local rails, fitting combined and standalone motion, isolated supplier parts and an actually invoked useful native asset. It must also test scope, inheritance, evidence and delivery workflows. An individual product need not contain that entire portfolio. Existing historical observations retain their original identities and limited scope; this catalog does not revise their statuses.
