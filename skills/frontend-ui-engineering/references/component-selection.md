# Component discovery and selection

Read before choosing external UI parts for a new surface, redesign, or unresolved visual treatment. Prefer suitable existing components to rebuilding them. This preference includes the project's installed components; it does not require replacing an approved working component or adding a dependency for ordinary HTML/CSS.

## Find parts for the idea

Start from the current brief, approved references and product system. Describe the visitor's task, the component's role, the intended visual character and the behavior that sells the idea. Carry forward relevant user preferences from [personal-design-defaults.md](personal-design-defaults.md) and [liked-motion-options.md](liked-motion-options.md). Separate approved qualities from hypotheses. A reader may benefit from a warm material and selection sweep; an operations dashboard need not inherit either.

Inspect local components and tokens first. For a new or unresolved part that local components do not satisfy, perform targeted resource discovery before inventing it. Use [resource-catalog.md](resource-catalog.md) to choose the relevant source class; browsing every site and every component is neither necessary nor a substitute for judgment. Search by component role plus theme/behavior and stack, rather than popularity or a vague request for a beautiful page. For example: “reading selection highlighter React controlled reset,” or “horizontal artifact gallery rounded clipping delayed image zoom.” Search the behavior as well as its visual name; a cube carousel does not satisfy a lateral slide.

Use available existing retrieval mechanisms: official shadcn registry search/view/examples for source; authenticated 21st discovery/inspiration and previews when available; GodUI or Fancy registry/docs for targeted motion parts. The 21st build/explore skills already demonstrate project-aware reuse and comparable exploration; use those capabilities when installed rather than creating a second implementation pipeline. Keep this skill as the design authority and do not install an overlapping suite wholesale. If a connector is unavailable, browse public demos and permitted upstream source directly. A catalog entry does not establish tool availability, account entitlement or an accessible code license.

## Choose with evidence

Inspect each credible finalist's actual demo and source. Explain its fit in concrete terms: how its anatomy supports the task, how its material/type/color can join the existing system, and whether its interaction matches the required behavior. Include meaningful limitations and needed adaptations. Reject an attractive example when its behavior, layout or dependency cost defeats the intended role. Preserve a small defensible shortlist; stop when it makes the decision reviewable. If useful matches cannot be found after a focused search and one relevant alternate source, explain that gap and use the simplest appropriate local composition. Do not browse indefinitely or build a poor approximation merely to satisfy reuse.

Source delivery and theme extraction have different jobs. Use component code for working UI, live computed CSS for observed values, and screenshots for appearance. A DESIGN.md kit can seed typography/color decisions; it does not supply component semantics, responsive formulas or hidden states. getDesign/community kits contain inferred choices. For numerical reference measurement, inspect live computed CSS or use an existing extractor such as Dembrandt when available; do not build a new screenshot scraper. Verify fonts, viewport and relevant states. Treat extracted token grouping and screenshots as evidence, not the original designer's intent.

## Show parts before integrating them

Follow [taste-selection.md](taste-selection.md) for delivery and selection. For this user, show proposed new UI parts before product integration by default: present the scoped isolated demo before changing the actual page. Delegating the aesthetic choice alone does not waive this parts preview. An explicit current request to skip that preview can waive it; routine repairs within the approved system need no new parts-selection round. A source/catalog demo can establish the candidate's behavior; unresolved appearance after adaptation needs a demo with representative product content, typography and tokens. Motion requires a playable preview. Links to catalog homepages, unshared captures, a prose list or code diffs alone do not satisfy visual delivery.

For each shown part, keep a compact record in the project's existing design context: source/item and license, intended role and liked quality, necessary adaptations/dependencies, observed preview and limitations, and selection status. Explain the recommended starting point. Let the user choose or combine qualities, reject them, or delegate a provisional decision. Do not equate approval of one effect with approval of the source's whole theme. Retain chosen/rejected qualities at their stated scope so the next search starts with evidence rather than another arbitrary choice. Existing approved parts and routine repairs need no fresh resource search or selection round; rendered review before commit still applies to appearance changes.

Before importing, inspect the exact source, dependencies, global styles, framework compatibility, accessibility and responsive/reduced-motion paths. Prefer a registry preview/dry-run/diff when available; those inspect file changes, not rendered quality. Stage adaptation in the isolated preview, then integrate the selected part after the required user review or explicit waiver. Keep the project's semantic tokens, primitives and behavior contracts; replace incidental demo text and hardcoded styling rather than importing a whole house aesthetic.

Check selected-item rights, not only the library's license. Link official catalog previews when reuse is restricted; do not mirror marketplace media. Account/quota limits are operational facts to recheck, not permanent instructions. Inspect available quota before a metered source retrieval and avoid spending it on discarded alternatives. Do not buy access or invoke separately metered hosted AI under a component-browsing request.

When a useful background or illustration cannot be reused or found at suitable quality, use the authorized native image-generation route described in personal defaults. Generate a fresh asset suited to its actual job rather than reproduce another site's branded artwork. Prefer the latest supported GPT Image route and leave an unverifiable backend version unverified. Preserve functional UI as real components. Review texture strength, seams, readability and light/dark behavior in context before replacing an approved asset.

## Existing foundations

- [shadcn MCP](https://ui.shadcn.com/docs/mcp) and [CLI](https://ui.shadcn.com/docs/cli): registry discovery/source and change inspection; no rendered-quality guarantee.
- [21st MCP](https://21st.dev/mcp.md), [build](https://21st.dev/.well-known/skills/21st-ui-build/SKILL.md), [explore](https://21st.dev/.well-known/skills/21st-ui-explore/SKILL.md): project-aware supply and comparable previews; account and client preview support vary.
- [Emil's prototype](https://github.com/emilkowalski/skills/tree/main/skills/prototype): isolated component exploration before promotion. Borrow this separation, without fixed variant counts, forced picker markup or universal timing rules.
- [Dembrandt](https://github.com/dembrandt/dembrandt): optional live observed-token extraction, not recovered functional components.
