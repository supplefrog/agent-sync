# Career and Portfolio Positioning

Build a credible hiring story from the user's desired work and demonstrated capabilities. Keep candidate-specific facts and changing application state in the career project's profile/evidence files, not this skill.

## Procedure

1. **Establish the destination and exclusions.** Separate desired daily work, tolerated transition roles, and work the user wants to leave. Treat current employment as evidence, not destiny: do not recommend the same unwanted specialty with an AI label. Check operational burden and on-call expectations as well as job titles.
2. **Inventory existing work before prescribing projects.** Inspect the user's GitHub and relevant local projects, including hobby tools, substantial customizations, integrations, and upstream contributions. Ask about missing examples only after using available evidence. Prefer strengthening an existing demonstrable project over inventing another portfolio obligation.
3. **Build a bounded evidence ledger.** For the strongest few artifacts, record a source link, concrete implementation, user's contribution, verification available, and claim limitations. Use `github-collaboration-workflows` for repository/PR inspection. Distinguish original code, adapted material, configured capabilities, proposed changes, and merged contributions; repository ownership alone does not establish authorship of every component.
4. **Map evidence to real roles.** Compare actual requirements with demonstrated programming, debugging, integration, testing, and design work. Separate confirmed strengths, plausible transferable skills, and gaps. Keep fast learning as a hypothesis supported by examples—not a substitute for years of production experience. A design interest is a potential direction, not completed professional work.
5. **Choose a focused narrative without erasing breadth.** Lead with the strongest relevant engineering work. Keep official employment titles and actual responsibilities truthful; personal projects belong in a separate section. Do not inflate hobby work into employer delivery or infer background-check disclosure from an internal HR label.
6. **Draft claims with evidence attached.** Use implemented behavior and measured outcomes. Never promote rejected claims from an old AI-written resume into the factual source of truth. Verify each achievement independently; one tested contribution does not justify calling an entire portfolio test-backed. Preserve uncertainty about authorship, deployment, adoption, and metrics.
7. **Recommend the smallest next improvement.** Prefer a clear demo, reproducible setup, regression tests, or a concise explanation of existing work when those close the hiring gap. Propose a new project only for a specific missing requirement and in a domain the user actually wants to pursue. Future exploration remains future work until artifacts exist.

## Resume comparison

Preserve original source bundles, but do not confuse preserving originals with retaining every formatting macro in generated variants. LaTeX command names are not ATS credentials; evaluate the resulting document.

When comparing variants, hold content fixed for layout tests and layout fixed for wording tests. Keep factual accuracy, extracted-text quality, JD requirement coverage, visual readability, and proprietary scores separate. Compare revisions using the same scorer and target JD; a larger number from another vendor is not evidence of a better resume. Do not invent unavailable feedback or present a local structural heuristic as an employer's ATS result.

## Output

Lead with the strongest supported positioning and the evidence that changes it. Provide a short ranked artifact list, defensible claim examples, and concrete gaps. State which artifacts were inspected versus executed and which contribution statuses remain pending. Save the detailed ledger locally; do not make the user repeat information already available in their repositories. Career research does not authorize public profile edits, resume uploads, or application submission.
