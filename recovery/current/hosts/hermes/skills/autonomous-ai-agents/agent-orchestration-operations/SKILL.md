# Agent Orchestration Operations

Use this umbrella for multi-agent coordination that extends beyond one direct Hermes response. Choose the branch by execution surface.

## Fresh-chat invocation

- **“Resume the orchestrator.”** Load this skill and recover the active control-plane source plus any directly referenced sessions/artifacts before reconstructing work. If the current deployment explicitly uses the `agent-orchestration` Kanban board, treat it as the temporary live task source and reconcile it with original decision/artifact evidence; do not assume Kanban is the permanent substrate or create a duplicate plan. Continue the highest-priority actionable work.
- **Calling this agent “the orchestrator” and adding work.** Treat that as a role assignment, not a magic command. Accept ordinary phrasing such as “also handle X,” reconcile each outcome against existing board ownership, and deduplicate/enqueue it without making the user restate a template.
- **“Orchestrator status.”** Read the explicitly selected control-plane source and reconcile direct artifact evidence. While the current deployment uses Kanban, include the live board, gateway, caretaker trigger/repair state, and active worker/descendant activity; do not turn those implementation details into permanent product requirements. Report authoritative state rather than dashboard appearance. Reconcile every material nonterminal workstream plus material changes since the last brief. Call an item **working** only after readback proves a current run and live PID/heartbeat or equivalent activity; `ready`, staged, assigned, or spawned alone is not working. Verify each assignee maps to a live spawnable profile. If the highest-priority actionable lane is stranded and no user decision is required, recover it through supported assignment/status/dispatch surfaces and verify the resulting claim before reporting. Use the stakeholder-brief contract in `references/human-off-control-plane.md`.
- Session todos are a convenience view, never the durable orchestration authority. Use **repeated blocker** for the dashboard-visible condition; reserve **circuit breaker** for implementation-level explanations and define it when needed. Ask the user only for an exact unresolved decision that changes the correct action.

## Shared contract

1. Define a bounded outcome, authority, artifacts, and acceptance checks.
2. Preserve source provenance; treat a thread-local implementation—even with passing narrow tests—as partial evidence until it is reconciled against the broader goal, competing implementations, lateral work, and regressions.
3. Normalize every effective writable root before dispatch. Same-root writers serialize unless independently isolated; prove a baseline commit before choosing a Git worktree, otherwise use a runtime-owned temporary copy or serialization.
4. Separate intake/control, producer, independent-reviewer, and stakeholder contexts. Carry work across Hermes, Codex, OMP, DAGs, and optional task-local runtimes through an agent-neutral packet containing outcome, constraints/approvals, state, dependencies, decisions, provenance-backed evidence, acceptance checks, unresolved questions, and next action. Use the explicitly selected control-plane source plus referenced original artifacts as authority; chats, reasoning traces, summaries, dashboards, and task cards are lossy projections unless the current architecture explicitly assigns one of them authority. When the user refers to prior work, search session history and inspect the recovered direct artifacts before creating or reconstructing anything. Verify that another supported host can resume without the originating chat.
5. Keep parent-owned architecture, authorization, integration, and final verification explicit. Delegated-child guards remain strict, while child context/identity must reset at the boundary so the parent retains controller authority.
5a. For a broad meta/architecture outcome, keep one durable parent as decision/integration owner and let brainstorming plus research refine intent before freezing a DAG. Decompose independent evidence, comparison, implementation, and held-out verification lanes only after their interfaces and gates are explicit. A worker may recursively expand/spawn the DAG only when the surface provides parent-visible typed child handles, bounded depth/fan-out/budget, isolated writable roots, retained receipts, failure propagation, and verified cleanup; otherwise the controller owns graph creation and children remain leaves. Route each node from its exact requirements and persist its provider/model/reasoning/runtime receipt. If native DAG/session lifecycle is red, retain durable dependencies and serialize through a proven surface rather than simulating concurrency or asking one opaque child to handle the umbrella.
6. Treat dispatch, execution, review, completion, delivery, and reconciliation as distinct states. Submit verification-ready work to native review; reserve `blocked/needs_input` for one unresolved user decision, not completion review or external watching.
7. Verify artifacts, diffs, tests, process state, external readbacks, and remote writes independently. Run deterministic checks before paying for a reviewer model. When a broad regression batch is already red, run the identical command in a disposable clean worktree at the exact baseline commit, compare failing test identities and mechanisms rather than counts, and isolate changed-path tests in fresh processes when shared module state contaminates the batch. Zero new failures is evidence of parity, not a green suite and not permission to bypass an explicit clean-suite promotion gate; preserve the evidence and remove the disposable worktree. A comparison is not terminal until every credible finalist is exercised or excluded by a verified hard constraint; an unrun candidate means **comparison incomplete**, not “no winner.”
8. Close temporary workers and preserve only useful evidence handles. For intentional supersession, archive/cancel the durable task before or atomically with terminating its process; killing it first looks like an ordinary crash and can cause recovery to respawn obsolete work.
8a. A Kanban worker's textual report is never its terminal transition. Before yielding control, write/verify any requested artifact and invoke the authoritative `kanban_complete(summary=..., artifacts=[...])` or `kanban_block(reason=...)` tool with the worker's current task/run identity. Do not substitute a prose claim, a local test result, or a future promise; if the board tool is unavailable, treat that as an explicit operational blocker rather than silently ending.
9. Keep routine board care autonomous. Resolve deterministic states without user steering; when judgment genuinely changes the correct action, surface exactly one reconciled question and never ask the user to inspect the board. Never label or persist a comment as a user decision unless the current user message unambiguously answers that exact question; synthetic fixtures, evaluator text, agent inference, and empty clarification responses are not user provenance.
10. Preserve transparency without interruption: write completion/repair receipts to Kanban; automatically deliver short stakeholder briefs when work starts, materially changes direction, enters review, meets a genuine blocker/decision, is promoted, or completes. Batch routine/no-impact transitions and deduplicate unchanged state. On every status request, reconcile **all material nonterminal workstreams plus recent decision-bearing terminal changes from Kanban/events**, never from chat recall or only the currently discussed lane. Status uses **done / working / waiting / needs you**, leads with whether the approved outcome is live/staged/not started, and preserves material failures, no-promotion decisions, dependencies, and next transitions. Label a lane **working** only after readback proves a live claim/run and fresh activity; `ready`, assigned, staged, or planned is not working. Validate that every dispatch assignee is an existing spawnable profile; autonomously recover/reassign an invalid assignee through supported policy or surface the operational blocker, never leave a phantom lane for the user to discover. A material omitted lane, a false claim of motion, or a user reminder required to trigger routine reconciliation is an orchestration regression. Keep briefs free of code, diffs, logs, card IDs, and internal reviewer/caretaker vocabulary unless requested. Distinguish assistant prose from Desktop-rendered tool receipts; verify Product/Technical display mode before treating residual receipts as an upstream UI gap, and never add prompt hacks to hide UI-owned output. Approval, design, tests, staging, and live implementation are distinct states.
10a. Schedule bottleneck-first. Derive the current critical path from live acceptance gates, dependencies, review blockers, writable-root conflicts, spawnable profiles, and downstream impact—not from title similarity, chat recency, or priority numbers alone. Keep the highest-leverage actionable bottleneck actively claimed; if it stops without a genuine decision, reconcile and resume it before unrelated work. When the user says **fast-track**, persist and read back the explicit lane order, serialize a single spawnable profile accordingly, and verify the next lane becomes active after each terminal transition. Event-gated maintenance with unchanged-output suppression may remain scheduled because a no-change tick consumes no worker/model lane; pause it only when live evidence shows contention.
11. Treat natural additions such as “I might have added X” as intake, not a command-template gap. Reconcile both durable board ownership and live capability state before creating work. If the requested install is already enabled, do not create an install card; route verification, overlap, or discoverability work instead. When a new capability could contaminate a behavior baseline, serialize baseline evaluation before admission or installation.
12. After broad changes across agent surfaces or repeated model-specific corrections, load `cross-agent-surface-engineering` and require its effective-stack inventory, lean-baseline retirement gate, held-out evidence, coherent-owner decision, rollback, and fresh-host receipt before promotion. The orchestrator schedules and enforces that audit; it does not duplicate or weaken the owning procedure.
13. When substrate authority is open, compare credible complete systems against the same user outcomes and constraints. Compare whole-system guarantees before treating a contender as a component source. Choose retention, replacement, native ownership, or extraction from decision-relevant evidence and integration cost; do not mandate named contenders independently of the task.
14. Give material architecture or irreversible direction one bounded adversarial review: present the strongest credible alternative, attack authority boundaries and failure modes, and seek decision-changing evidence. Stop when objections are resolved or converted to explicit risks/tests; do not add performative debate to routine execution or reopen settled choices without new evidence.
15. For recurring, consequential, or explicitly requested orchestration failures, trace the decision and state transitions to the owning mechanism, fix affected paths within scope, and verify the failure plus nearby valid behavior. Use independent review when risk warrants it. A correction alone does not authorize a durable RCA or global lesson. For failures in a control plane that implements research-gated promotion, use `references/research-first-intake-gates.md`.

## Session lifecycle cleanup

Use one runtime/spawner-owned lifecycle registry for every agent surface; do not put cleanup policy in individual skills, workflow definitions, or one-time cleanup cards. Cleanup is continuous: evaluate task-related threads whenever their task becomes terminal and agent-spawned threads whenever their owner integrates the result or no longer needs them. At spawn, issue an explicit opaque ownership token and persist the parent session ID, child session ID, owner process identity (PID plus process-start token), terminal state, and integration state. A source tag such as `tool` is classification/filtering metadata, not deletion authority.

Delete a child session only after its useful result is explicitly integrated and a transactional re-check proves that the ownership token still matches, the child is terminal, no process/turn/lease remains active, and no user adoption, sharing, pin, or reference exists. If any check is uncertain, retain it. A user resume/message/title/export/pin/share action adopts the session as durable. Crash recovery should mark ownership abandoned/unknown first; it must not infer that an unobserved child is safe to delete.

Before requesting destructive approval, explain what every candidate parent and child thread was about, its outcome, and whether failed or partial work was explicitly superseded. Titles, IDs, counts, and terminal flags alone are not an intelligible cleanup plan. Ask for scoped confirmation only after this semantic inventory, then preserve the user's selected parent/child boundary exactly.

For external or durable runners, the host adapter should only register the spawn, propagate the lifecycle identity, record the returned child session ID, and emit an integration acknowledgement. The central runtime owns cleanup. In particular, the local DAG runner currently passes `--source tool` and tracks subprocess PIDs/outputs but has no runtime-issued ownership identity; process reaping is not session cleanup. A session ID, source, stdout line, title, cwd, timestamp, or parent link alone is never deletion authority. See `references/session-lifecycle-cleanup.md` for the audit evidence and typed adapter contract.

Use ordinary direct execution when delegation adds no capability, isolation, or throughput advantage.
