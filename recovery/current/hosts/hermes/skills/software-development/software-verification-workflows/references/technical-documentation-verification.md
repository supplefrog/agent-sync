# Technical documentation verification

Use for manuals, administration notes or cross-product/platform documentation acceptance. Reuse the project's authoring and citation owners; this reference owns acceptance, not a new writing style, platform default, worker policy or website redesign.

## Bind the corpus and operating assumptions

Read the complete brief/source inventory. Account separately for preserved, corrected and new material; a representative preview is not the corpus. Record applicable product/version, edition, platform/architecture, package origin and operational dependencies. Verify support and entitlement independently. Keep platform-neutral and separately scoped platform material intact.

## Verify task parity and platform applicability

Map usable procedures, options and explanations to destination sections. Compare prerequisites, privileges, examples, expected observations, diagnosis, rollback and recovery rather than headings or chapter counts. Track product-specific obligations and explain real non-equivalence.

For platform migrations, trace the affected deployment chain: package/repository/signature setup, initialization, service identities, binary/config/data/log/socket paths, host security, instances, relocation, backup/restore, replication and upgrades. Changing installation commands alone does not establish parity. Check platform security controls without making their disablement the default.

## Bind evidence and regeneration

Use official version/platform-specific sources for operational claims. Citation presence alone does not prove applicability or support. If extraction mixes platform tabs or contradicts commands, check the selected rendered variant and authoritative package/service definitions. Label unresolved uncertainty.

Identify which hashes cover raw HTTP bytes, extracts and final content; retain their distinct historical meaning. Edit owning inputs/generators and regenerate before checking final manifests. Later changes invalidate affected receipts.

## Separate acceptance layers

Use the project's actual checks in dependency order: inventory/coverage; evidence and substantive procedure review; generation/footers/manifests; independent link/anchor/fence/table/nonexecuting syntax checks; reader compilation and browser checks against final manifests. Do not introduce absent tooling solely for this list.

Inspect mapped content rather than empty anchors. Check rendered code text and malformed fences that can swallow later prose. Sample beginning/middle/end passages for readability and task completeness. Accessibility and overflow checks do not establish technical correctness.

Distinguish inspection, mutation, disruption and destructive recovery examples. Expected output must be labeled as expected. Documentation work does not authorize executing operational commands, labs, publication or a reader redesign. Report source preservation, substantive coverage, platform applicability, reader behavior and operational execution separately; say reviewed/not executed when no authorized lab ran.
