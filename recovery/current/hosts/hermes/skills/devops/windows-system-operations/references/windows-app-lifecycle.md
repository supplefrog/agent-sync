# Windows application lifecycle

## Store routing and package repair

Read Store and AppX operational events at the failing timestamp, test the exact URL with the system resolver, compare independent resolver answers, and use `curl.exe --resolve` to test alternate routing while retaining TLS hostname. An HTTP 401/405 can prove transport reachability. If temporary DNS is required, an elevated helper must save/apply/restore adapter DNS in `try/finally`, while the Store install remains in the normal interactive-user process.

Treat `Modified, NeedsRemediation` as package-integrity evidence. Re-registering a manifest repairs registration only; a same-product forced Store reinstall may repair files while preserving package data, but completion still requires `Get-AppxPackage` status, location, and `Get-StartApps` readback.

## Electron/Chromium crash boundaries

Keep symptom, trigger, first failing process, underlying root cause, consequence, mitigation, and durable fix separate. Correlate fresh logs, WER/Crashpad, child-process events, package state, and the exact route. A browser-process breakpoint after a GPU child crash is terminal evidence, not the child root cause. Verify diagnostic switches in main and child command lines and reopen the exact failing route long enough to exceed the prior crash window.

Do not weaken Code Integrity globally. When fallback DLL signing is suspected, inspect Code Integrity events, Authenticode/catalog coverage, and the live child signature policy. Clearing persisted browser tabs can contain a boot loop but does not repair GPU/signing failure. Never attribute native runtime failure to a missing instructional skill.

## Privacy-preserving uninstall

Inventory process/port, uninstall/package entries, PATH commands, app-owned global auth/config/session/cache/log/updater/temp state, credential-manager target names, registry keys, and shortcuts without printing secrets. Preserve project-owned instructions unless project cleanup is explicit. Stop processes, use the registered uninstaller, remove portable/app-owned global state, then verify every applicable process, port, package, command, data path, credential target, registry key, updater path, and shortcut is absent. Local token deletion is not provider-side revocation or forensic secure erasure; state those boundaries precisely.

## Home-folder remnants and misplaced checkouts

1. Start with a shallow home inventory of names, file sizes, directory types and reparse attributes without opening credential contents. Correlate candidate owners with HKCU/HKLM uninstall records in both registry views, `winget list --disable-interactivity`, `Get-AppxPackage`, relevant package-manager inventories such as `npm list -g --depth=0`, PATH lookup, and standard executable locations. Filter these inventories to candidate owners before presenting results. Missing PATH or installer records alone establish only a likely leftover because portable and app-managed runtimes can remain.
   - Inspect candidate directory structure before assigning risk: separate redownloadable caches from local package repositories, custom configuration, credentials, sessions and worktrees. A missing application executable or empty install folder does not make its user data disposable. Shared roots such as `.cache`, `.config` and `.docker` require per-subfolder ownership checks. Before removing a package-manager home, inspect its global-package subtree; an absent executable does not establish that installed packages are disposable. For Windows Docker cleanup with WSL retained, classify executable format, container-state paths, contexts and plugin targets; preserve WSL-targeted binaries and shared configuration rather than treating the Windows home location as proof of Windows-only ownership.
   - Measure only plausible candidates, skip reparse points, and report skipped links, access failures and bounded-scan truncation; distinguish logical file bytes from reclaimable disk space. Save structured results and give the user a compact path/size/owner/evidence/consequence table plus a shortlist, not a dump of every installed application.
   - Explain normal loose shell/Git/WSL configuration and protected Windows registry files before recommending cleanup. Separate obsolete setup fragments from active credential stores; a deployment repository is not a backup of private administration credentials. Remove only approved targets after rechecking their identities and exact contents; use bottom-up `rmdir` for empty ancestors so unexpected contents stop deletion.
2. For SQLite remnants, explain that `-wal` can hold committed changes not yet checkpointed and `-shm` coordinates WAL access. Require the corresponding main database to be absent and every candidate WAL to be empty. On Windows, acquire all candidate files with `CreateFileW` using DELETE access, share mode zero, and OPEN_EXISTING before deleting any; stop on a sharing violation. Mark deletion through `SetFileInformationByHandle(FileDispositionInfo)` while holding the handles, then close and verify absence. Never apply this orphan-file recipe to an active database's companions.
3. Discover repositories once without following reparse points; save the inventory and inspect files outside repository roots. For each checkout collect `git status --porcelain=v1 --untracked-files=all`, local branches via `git for-each-ref refs/heads`, `git worktree list --porcelain`, and ignored files via `git ls-files --others --ignored --exclude-standard -z`. Summarize counts and exceptional paths rather than printing full remote-ref lists or thousands of deletion records. An empty index with a metadata-only checkout is different from uncommitted source changes; verify the actual files before classifying it.
4. Check active process cwd, saved workspace metadata, external worktree links, and mount targets before disposal. Compare every local branch tip with reachable commits in maintained repositories. Run `git rev-list --all` once per maintained repository and test membership in code instead of spawning a Git process for every commit/repository pair. Commit age, clean status, or object presence without a retained ref does not alone establish recoverability.
5. When unmatched commits affect a supersession decision, compare their diffs with the retained canonical branch before creating recovery duplicates. Use `git show --format= <commit> | git patch-id --stable` to identify equivalent patches under different commit IDs; trace the current call path and run focused behavior checks when refactors prevent a direct match. Ancestry absence alone does not prove a missing behavior. Distinguish submitted/open from merged with live PR state rather than inferring it from a local remote-tracking ref.
6. If authorized cleanup needs recovery for unmatched branch tips, group worktrees by `git rev-parse --git-common-dir` and preserve each repository's branch set once. Create `git bundle create <bundle> <explicit-local-refs...>`, check `git bundle list-heads` against the inventory, and run `git bundle verify`. Confirm no prerequisite commits before calling a bundle standalone. Worktrees share branches: bundling each separately wastes space. Do not discard unique untracked, ignored, or dirty work merely because commits are recoverable.
7. Recheck HEAD, branch sets, status, target identities, and the exact deletion allowlist immediately before removal. Keep a receipt outside the deleted tree, remove only reviewed targets, and verify their absence plus retained recovery artifacts. Report retained exceptions and recovery bytes explicitly; do not describe archived unique branches as proven superseded.
   - If authorized deletion stops at a read-only Git object, inspect `lstat().st_file_attributes` before retrying. In a `shutil.rmtree(..., onerror=...)` callback, require a non-reparse file inside the approved target with `FILE_ATTRIBUTE_READONLY`, clear only the DOS read-only bit with `chmod(st_mode | stat.S_IWRITE)`, and retry that failed operation. Re-raise other failures; do not turn an ordinary read-only attribute into an ACL takeover or broader purge.
   - Resume a partial cleanup from the saved receipt, re-inventorying only unfinished approved targets and preserving prior successes. Verify every original target absent at completion; restarting the initial plan can fail on already-deleted prerequisites or erase evidence of partial progress.

## WSL remnants and setup recovery

1. Identify the exact path before treating a Windows folder as Linux state. `C:\wsl.localhost` is a local path; `\\wsl.localhost\<distro>` is a WSL share. Check reparse targets and inventory local files without following links; a similarly named directory does not prove the Linux installation survived.
2. Run `wsl.exe --list --verbose` before accessing the distribution. If it is stopped, explain that starting it to inspect files can also start configured services; do not silently turn a recovery inquiry into service reactivation. For inspect-then-stop permission, place `wsl.exe --terminate <distro>` in a host-side cleanup/finally path covering the entire inspection and verify `Stopped` afterward, including after an inspection error.
3. Inspect surviving setup structure without printing credentials. For Compose files, summarize service names, environment-variable names, build paths, and bind-mount sources; check that referenced Dockerfiles, source directories, and base Compose files exist. An override alone is a recovery fragment, not a runnable backup.
4. If source is absent, inspect Docker containers, volumes, images and Compose projects separately with `docker ps -a`, `docker volume ls`, `docker image ls`, and `docker compose ls -a`. Empty container/volume inventories do not imply that images are gone. Inspect selected image metadata without printing environment values, then use `docker create --network none --entrypoint /bin/true <image>` and `docker cp <id>:/app -` to stream a tar inventory without running the application. Remove the temporary container in `finally`. Compare expected Compose bind-mount paths with image contents: host-mounted custom code is not recoverable from a stock image merely because its tag says gateway or router.
5. Separate setup reconstruction from database recovery. Check surviving files and Git history first, then use exact prior conversation evidence to fill documented gaps; label reconstructed pieces rather than claiming an original backup. Preserve the original fragment until a replacement is verified or the user explicitly abandons recovery. Stop reconstructing minor features when the user closes that effort. Keep secrets and private database contents out of any proposed Git recovery package; publication is a separate decision.
6. For approved image cleanup, recheck exact tags and image IDs plus container references, remove only the allowlisted images without force or broad pruning, and verify unrelated tags remain. Do not remove shared base images or the distribution, or claim that image deletion shrank the Windows VHDX.
