# Capability-preserving package upgrades

Use for Hermes skill/plugin/package inventory and upgrades, including nested umbrella components. Preserve useful behavior while adopting current supported implementations; neither a blanket reset nor indefinite retention of an old package is the goal.

## Discover and establish provenance

- Identify active home/profile/runtime, native-discovered entrypoints, nested components, resolved mounts, plugin code, and state-only directories separately. Record installed, enabled, and reachable through an enabled umbrella as different facts. A nested component under an enabled owner must not be labeled unused just because its standalone entrypoint is absent. Exclude archives/caches and other profiles.
- Inspect entrypoints, supporting files, dependencies and callers. A custom umbrella may contain unchanged bundled components; evaluate each component independently.
- For bundled plugins, distinguish runtime-source drift from independently installed plugin updates. Record the owning updater, whether the package is installed at all, CLI enablement and any backend/provider selection caveat. A newly added upstream plugin is not an outdated local installation; a source hash difference alone is not an update requirement. Do not turn source inventories into automatic maintenance backlogs.
- Pin the upstream revision and compare full relative file sets/hashes. Search both bundled and optional upstream trees before mining history; moving a package to optional distribution is not removal. If a current upstream path is absent, use bounded ownership/history evidence when it affects replacement, licensing or safety. An upstream rewrite/removal is not proof of local authorship. A locally maintained/self-created skill with no upstream update contract is not unfinished maintenance merely because its original provenance is unknown; preserve it and repair concrete defects without creating an origin-hunting task for the user.
- Separate installed baseline, historical upstream baseline, local changes, and latest candidate. Hash equality proves duplication, not usability. Inspect supported updater/reset behavior before trusting it to preserve an entire package.

## Compare capabilities and choose the upgrade path

- Map old to new outcomes: formats, creation/editing, quality/style, edge cases, safety, offline/privacy/cost constraints, host compatibility, and caller/discovery integration. Guides/templates count when they materially enable work. Do not equate fewer files or renamed helpers with regression, and do not count broken legacy claims as working features.
- Classify: already current; upgrade candidate; local-delta merge; missing-capability migration; owner-managed; state only; provenance unresolved; inactive/do not enable. Inventory classification alone does not authorize publishing.
- If current upstream drops valued behavior, investigate a maintained replacement or narrow new integration and test the lost behaviors. Preserve the capability, not obsolete files. Hold only the affected component when parity is unproven, with the gap and reopening condition stated. Do not describe a held old version as a completed upgrade or dismiss advanced quality features as optional without the user's agreement.
- Preserve intentional local improvements even when upstream is newer. Review changes in instruction semantics as well as scripts: user steering, authorization, tool schema compatibility, and safety boundaries can regress in prose-only updates.

## Stage, verify, publish

1. Stage outside live discovery. Inspect source, license, commands and dependencies before running code. Use isolated dependency environments first; active-runtime installs, worker interruption, and stateful plugin reloads require scoped authorization.
2. Run upstream tests plus targeted baseline-capability and boundary probes. Reopen generated artifacts; render and inspect when visual quality is part of acceptance. When the user explicitly defers optional rendering dependencies, allow activation after the other gates pass; record visuals as unverified and require actual rendering when available rather than keeping activation blocked. Security gates remain independent. Separate code correctness, documentation coverage, and visual quality. Tests for the new implementation alone do not establish old capability parity. Verify that claimed migrations actually change the relevant installed/candidate symbols, not just their report or version label. Check supporting references too: an updated entrypoint may still link obsolete APIs; clearly separate any intentionally retained version-bound compatibility material.
3. Use independent review for reasoning-heavy gaps; use code for mechanical enumeration/hashes. Validate a new generalized workflow on an unrelated package/class before durable promotion. Keep counts reconciled against saved enumeration.
4. Publish with the supported updater only when it targets the correct owner/component without destroying customization or enabling unwanted packages. Otherwise narrowly merge/update at the owning source. Repoint absorbed components and preserve umbrella routing, persistent state, privacy and cost boundaries.
5. Read back exact targets, compare file sets/hashes, verify fresh discovery and the consuming call path, then run installed-target checks. Core-coupled or stateful plugins may require a separate maintenance/restart window: stage rather than hot-swap them.
6. Treat rollback copies as temporary transaction state, not default deliverables. Before creating one, record its exact path, the risk it covers, and the verification that ends its lifetime. Once the replacement passes installed-target and capability checks, remove that transaction's superseded copies in the same job and verify absence. Keep a concise source/revision and supersession receipt so later cleanup does not repeat the capability audit. If verification is blocked, retain only the necessary rollback copy with the blocker stated. Do not apply this rule to unique user data, conversations, or unrelated/unreviewed artifacts. An active component held for a verified regression is not an archival backup, but remains unresolved work.

Permission to inspect/update packages does not authorize paid inference, global resets, other profiles/hosts, core runtime upgrades, or state migrations. Mounted/shared sources belong to their owning checkout; do not replace functional mounts.

## Receipt

Record source revision, owner/path, baseline/candidate relationship, capability gaps and resolutions, tests/skips, installed verification, exact changes, and held items. Keep package inventories and task-specific receipts in the project, not global memory. Extend this owning reference rather than adding another upgrade skill.
