# Approval interruptions and task-authorization design

Use for source-backed review of approval behavior. This is an investigation procedure, not a claim that any proposed scope mechanism is implemented or secure.

## Procedure

1. Read the existing handoff and acceptance receipt first. Separate the original user outcome, accepted staged corrections and deployment authority. Preserve completed evidence; an independent transport fix does not establish fewer approval interruptions.
2. Inspect current official security documentation and the installed source identity. Trace the detector, classifier input, final approval owner, human-response producer, timeout handling and actual execution boundary. Record exact symbols/lines and source hashes; mark documentation/source disagreements rather than merging them into an imaginary contract. Symbol checks establish reference accuracy, not behavioral correctness.
3. Classify concrete interruptions before proposing a fix. Preserve the exact command and correlate the deterministic detector finding, guardian verdict/error, and human outcome separately; a manual prompt alone cannot distinguish escalation, malformed output, provider failure, or an interactive denial override. Trace execution-bearing flags rather than trusting a generic warning label: an interpreter's script-file flag can share an inline-code category even when later arguments request help. Check whether the guardian actually received the wrapper contents or only its path and arguments. Imported launcher behavior or prior kernel state absent from that input remains unknown, not a demonstrated guardian false positive. Uncorrelated provider errors are not a causal explanation; differently wrapped commands are not matched evidence of classifier reliability.
4. Follow the actual wrapper into its underlying native handler before redesigning approval policy. Recover structured tool-call arguments and earlier imported/helper definitions, not just the visible cell or summary. Compare direct native use against the wrapper's required guarantees using the native-path checks below. Prefer removing an unnecessary arbitrary-code envelope over expanding permission machinery; reject a design that cannot improve the concrete interruption it is meant to solve.
5. Only if the task genuinely requires new authority, compare existing operator policy, session/category grants, context propagation and file-safety facilities before adding metadata. Trace consent from the human control surface to the host-owned decision. Role-labelled messages, acknowledgements, caller-supplied principals and authenticated RPC connections alone do not prove human approval. Keep deterministic checks separate from model judgment; unresolved producer trust blocks issuance, not an excuse to build a general permission framework.
6. Review the proposed lifetime and dispatch semantics against the boundary checklist below. Clearly label new fields, APIs and schema changes as proposals. Define representative covered, refused and unknown cases, acceptance tests, migration and rollback without presenting unexecuted expectations as results.
7. Use at most the authorized independent challenge budget. Declare admission/attempt/request limits first; preserve real task risk and class. A parent/defer/refusal decision ends the attempt when retries or refresh are excluded. Do not relabel consequential design as routine evidence extraction to obtain a worker, and do not report a rejected launch as independent review.
8. Lead the handoff with whether the recommendation solves the user's original outcome. Present the exact smallest change, decisive evidence, limits and remaining decisions; place detailed owner maps and test matrices behind it. Keep design acceptance, implementation acceptance and deployment separate.

## Native-path checks

- Compare contracts before replacing a launcher: preserve route admission, attempt ownership, source/fixture isolation, lifecycle and required accounting. Distinguish actual HTTP sends including retries from constructed model requests; a cap on one does not bound the other. Retain an instrumented harness when its extra guarantees are required, without presenting the ordinary native tool as an equivalent replacement.
- Separate session creation, history seeding, prompt submission, queue admission and completed work. Use the native operation matching the desired transition; seeded history is not a running turn, and a queued acknowledgement is not execution. Preserve exact target identity and agent-origin attribution rather than forwarding agent text as new human consent.
- Inspect retry behavior in the native consumer as well as the removed wrapper. Reuse admission and dispatch without blindly inheriting UI recovery retries: after possible delivery, an unavailable receipt requires outcome inspection, not another submit. A denied operation cannot be retried through a different native entry point without renewed authorization.
- If no suitable model-facing entry exists, describe the smallest typed adapter as design-only. Limit its arguments to the intended operation rather than exposing arbitrary RPC, credentials or control flags; preserve recipient guards. Do not save an unimplemented adapter as a proven workflow or widen a continuation request into session creation, a scheduler or a permission system.

## Boundary checklist

- **Configured policy versus observed outcome:** `approvals.smart_policy` is operator-supplied classifier context, not enforceable task authorization. For an authorized adjustment, preserve harmless reads and test the original interruption plus nearby negative cases. Report configured mode, observed per-command decisions and measured interruption reduction separately; a classifier verdict, transport fix or cleaner label does not prove fewer prompts. Retire a temporary policy only when authorized and its exact value still matches, preserving other operator edits.

- **Authority versus context:** distinguish permission to supply trusted classifier context from permission to execute. A classifier APPROVE cannot establish root confinement or authenticate consent.
- **Final dispatch:** check effective arguments after middleware rewrites and again after human waits. Examine cached approvals, force flags, unattended/container shortcuts, direct handlers, inline tools and connector batches; checking only the first request can leave another execution path uncovered.
- **Expiry and refusal:** define the linearization point for revocation versus dispatch. Test late replies, queued calls, copied context and automatic retries. Do not turn a denied or expired approval into rephrased execution. After possible RPC delivery, an unavailable receipt means uncertain outcome—not permission to resend.
- **Restart and rollback:** test whether losing an in-memory grant silently restores broader defaults. Require an explicit fail-closed resume strategy; a deny-only marker is one design option, not existing authority. Old binaries that ignore new state need a controlled rollback plan.
- **Workers and kernels:** attenuate child roots, operations, lifetime and native capabilities; default inheritance must be explicit. Revalidate live authority per mediated call. Persistent globals, imported functions and copied active flags do not preserve valid authorization after revocation.
- **Paths and effects:** separate read roots from mutation roots. Check all multi-file targets and search traversal, backend identity, aliases, links and check/use races. Cwd, command prefixes, module hashes and ordinary Python syntax are not complete descriptions of effects; raw filesystem, network and subprocess access can bypass mediated tools.
- **Separate authority:** do not derive cleanup/history deletion, publication/deployment, secrets, spending/paid fallback or guard-control changes from a generic workspace grant. Distinguish deterministic exclusions from concealed effects that remain outside the stated threat model.
- **Efficacy:** stricter scoped file permissions may add prompts without helping opaque execution. If the acceptance requirement is unattended arbitrary code within guaranteed bounds, report that metadata alone is insufficient rather than quietly promising a sandbox.
