## Shared contract

1. Start from the user outcome, not a requested mechanism.
2. Recover any prior inventory, decision record, direct artifacts, and unfinished companion deliverables before rebuilding them. Inventory current native capabilities and overlapping owners, then identify which prior classifications depended on an incumbent, authority, or interaction assumption that has since changed. Track operational side-deliverables as separate acceptance criteria so the research lane cannot silently displace them.
3. Normalize the inventory to one row per user-visible capability before comparing products. Score the operational end state, not incidental means: discovery, benchmarks, catalogues, dashboards, config writers, and integrations are redundant when another candidate absorbs their useful function. Treat a base shell plus its extension distribution as one effective stack, collapse ordinary overlapping features, and require primary-source plus executable evidence for claimed differences. More named agents do not make a design more complete.
4. When a candidate's advantage is emergent from a coupled runtime—state, tools, sandbox, self-modification, recovery, and interaction loop—evaluate the intact system end to end before proposing component extraction. Do not rebuild a weaker facsimile inside the incumbent merely to reduce migration risk. Extract only after selecting the winning substrate, and only for a verified missing capability whose semantics survive separation.
5. Stage external or changed capability bundles outside live stores.
6. Evaluate baseline and candidate in fresh equivalent sessions with complete support files.
7. Promote one coherent winner only when it materially beats the baseline without critical regressions.
8. Separate portable procedure from host-specific adapters and repository packaging only after the substrate decision; do not assume portability is more valuable than a contender's native architecture.
9. Verify fresh-runtime discovery and one real task after promotion; preserve rollback and provenance.
10. Treat instructions as model-versioned scaffolding: after a changed stack becomes active, statically filter first, then test only model-sensitive owners as bare versus full and full-minus-unit. Tie favors deleting generic steering; stable procedures and protected guarantees do not reopen on model name alone. Cache the exact stack, unit, suite, and harness hashes instead of running a whole-library LLM curator.
11. Audit the trigger separately from the planner: a release/catalog signal may start route research, but instruction re-evaluation should start only when the effective active route stack changes. Persist an active-stack fingerprint so alias movement, provider snapshots, and policy changes are not missed or conflated with merely listed candidates.
12. Treat cache reuse as an effective-stack claim, not a model-name claim. Include or prove equivalence for host, provider/transport, model snapshot, reasoning/decoding, prompt assembly/context, tool policy/schema, runtime, seed, and trial count. Default receipts to host-scoped; share a winner across hosts only after equivalent-stack proof and required-host behavior gates.
13. Before publishing a benchmark winner, expose the exact arm setup: runtime-resolved model/window/thresholds, request and trial counts, provider-measured versus estimated tokens, whether each arm retained raw input or replayed a compacted artifact, and which lifecycle/cache/session fields were actually observed. A hard-coded result field, two-request median, code-contract test, or synthetic estimate is not model-quality or restart evidence.
14. Treat larger raw windows, compaction, retrieval, and external memory as different mechanisms. Compare them at workloads that cross the relevant boundaries; a compacted base arm and an uncompacted large-window arm answer different questions. If the evidence supports different winners by workload, publish a conditional policy rather than forcing one universal winner.
15. In memory-provider comparisons, architecture documentation proves mechanisms, not relative user-understanding quality. Match the ingestion/retrieval model stack and recall/retention mode, isolate each arm's state, distinguish explicit-tool from automatic-retention lanes, and publish no winner until both arms are credentialed, healthy, and exercised on the same held-out cases. Clean up temporary services, sessions, banks, peers, and keepalives after the run.
16. When real demand for a persistent capability is uncertain, test marginal utility against the user's actual baseline before running provider shootouts or public benchmarks. A capability can work and still fail admission because it rarely changes downstream outcomes or costs too much context, latency, maintenance, or attention.
17. For gateways, routers, and aggregators, separate availability from dependability. More backends and hidden fallback may increase request completion while degrading model identity, output consistency, tool behavior, latency, privacy guarantees, and reproducibility. Admit a serious-work default only when the stable execution contract is proved; otherwise classify it as a bounded sidecar, explicit fallback, or experiment with fail-closed limits. Use `references/operational-infrastructure-fit.md` for the decision checks.
18. Do not interpret every “you forgot” or prior-thread complaint as demand for semantic memory. Deduplicate continuation copies, classify the authoritative owner first—repository/docs, task state, handoff, skill, curated profile, exact transcript search, or external memory—and count only cases where external memory is both the proper owner and changes the downstream result.
19. Measure capability context cost in three lanes: fixed system guidance, fixed tool-schema exposure, and dynamic retrieved/injected content. Resolve omitted configuration defaults from source/runtime state, verify the active provider after experiments, and re-measure in a fresh session because a live session may retain its startup toolset after configuration changes.
20. Close reversible decisions transparently: distinguish disabled or deferred from disproven, separate observed evidence from unobserved plausible use cases, persist the incumbent and concrete reopen triggers, and do not schedule periodic re-evaluation. A live use-case detector is a separate capability from storage/owner routing and must earn admission from repeated concrete misses rather than speculative completeness.
21. Evaluate single-agent suitability from enforced mechanics, not labels or reusable fragments. Mandatory profile creation, coordinator-only roles, worker delegation, shared queues, or multi-worker task graphs mean the capability is not genuinely single-agent even if one agent can reuse its intake or templates. Compare cross-host analogs by outcome and destination: an integration-native capture workflow may beat a generic extractor for direct writeback while remaining weaker at source provenance, ambiguity handling, or arbitrary-document coverage. Verify installed and enabled state separately before calling an analog available.
22. When evaluating model routing, trace the effective call path rather than inferring behavior from model names or marketing labels. Separate local aliases and context-budget metadata from the wire model and backend behavior; separate deterministic subsystem task keys from semantic prompt classification; and separate transient delegation, durable DAG scheduling, and provider-native multi-agent modes. Inspect the live tool schema and route-resolution precedence before claiming per-call or per-child control. When the user asks only what a mechanism means “in principle,” answer with the governing mechanism first and omit operational detail unless it changes that mechanism.
23. Before proposing a local patch for a missing agent capability, search upstream issues and pull requests for the canonical request, duplicates, competing implementations, and maintainer policy. Distinguish an engineering gap from an explicit authority or security decision; prefer an operator-authorized named-route design over free-form model-selected provider or endpoint strings when heterogeneous routing is needed.
24. For proxies, compressors, retrieval sidecars, and MCP add-ons, verify the integration on the exact released artifact and active provider path before installation. Repository modules, plugin prose, a generic compatibility matrix, or a passing SDK benchmark do not prove that the shipped CLI exposes the wrapper, that traffic traverses it, or that retrieval occurs before the model pays the context cost. Run a reversible no-config probe, compare marginal utility against native compaction and bounded tools, inspect persistent state created by the probe, and clean it up when admission fails.

For prose behavior evals, deterministic checks should enforce artifacts or true invariants, not require exact words that valid answers can paraphrase.

Use `skill-creator` for local lifecycle maintenance after admission.
