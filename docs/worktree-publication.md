# Worktree publication

Independent changes develop in separate Git worktrees based on the published commit. Only committed ready changes enter publication; development branches, indexes, and unfinished files remain untouched. Worktrees use the existing repository, remote, permissions, and reconciler rather than a separate scheduling service.

Create a development worktree from the discovered published source with Git's normal `worktree add -b` command, outside live skill discovery. Commit only the authorized, checked change. In that development worktree:

```text
python tools/run.py reconcile plan --ready COMMIT --adopt OWNER --include FILE
python tools/run.py reconcile sync --ready COMMIT --adopt OWNER --include FILE
```

Repeat selectors as needed; an owner or exact-file scope is required. Owners must already be admitted. Includes select reviewed publication content and do not expand the configured fleet or admit capabilities. Default sync completes distribution to the existing configured targets; deliberate source-only publication requires `--source-only` and remains rollout-incomplete. The ready input freezes a linear, non-merge commit range from its public base and rejects unselected paths. Uncommitted work is outside that range.

Readiness checks run before the common Git-directory publication lock. Once ready, a caller waits up to 120 seconds, fetches the latest configured upstream, and uses Git's three-way cherry-pick to compose its changes in a tool-owned integration worktree. Independent edits, including separated hunks in one file, merge normally. Real conflicts stop the affected change before deployment, retain its ready identity and conflict evidence, and release the integration lane for independent work.

The existing reconciler then checks, deploys, commits, pushes, and verifies the exact selected result. Development can continue during this serialized publication. Hash-only generated metadata is recomputed for the selected scope instead of coupling independent changes through aggregate hashes. Policy and selected same-source readback changes require explicit manifest review.

The shared Git directory contains two tool-owned worktrees:

- `agent-signal-integration-worktree`, branch `agent-sync/integration`, composes and publishes ready changes.
- `agent-signal-published`, branch `agent-sync/published`, holds only verified published commits and is the durable source agents discover through the managed skill manifest.

The published source stays stable during composition, conflicts, and an unsuccessful push. After publication, it advances to the verified commit, its fleet snapshot is rendered and applied to every configured root, and fresh native catalogue/body readback verifies configured hosts. Managed global source provenance moves there under existing root locks and state identity checks. Origin migration is restricted to the same shared Git repository and preserves installed content and owner records. These paths are maintained state, not temporary candidates to delete. The launcher reuses the primary checkout's dependency-ready runtime for linked worktrees; it installs nothing.

Before composing or deploying, the common-directory journal records the frozen ready input and selection. A failed deployed or published attempt retains that journal and the existing publisher's pending receipt. Retry the same command; every publication path, including legacy and native maintenance, honors that pending attempt. A publisher receipt records `published`, not `synced`, and stays durable through source refresh and configured rollout. Per-target verification and recoverable backups extend the same integration journal. A retry checks installed state and applies only remaining changes; a crash after push does not replay completed mutations. Unavailable or conflicting targets keep the result incomplete while independent targets finish. A failure while refreshing published source, native verification or provenance resumes that phase. Repeating an ordinary sync with the same source selection resumes its recorded published rollout; a different selection remains blocked. Clean unchanged repeats recognize the owned published cache only after checking its commit and installed state, then reverify the remote and native catalogues. Retry checks reject integration edits and extra files outside the frozen composition. Unexpected worktree identity, HEAD, index, source, or state changes stop rather than overwrite outside work. Never reset pending integration or rewrite remote history.

Resolve a source conflict in the development worktree and submit a new ready commit. Explicit legacy working-file publication uses `--shared-checkout`. Native capture and configured-default changes remain on the existing native maintenance path without `--ready`, in a development checkout with the correct upstream; the stable published source rejects direct maintenance. Exact source-authored generated overlays may be included, then restored through the native recovery owner. Ready integration rejects capability admission and lifecycle changes even through exact-file selection, and does not change provider, authentication, or running-session defaults.

An owner-classification rejection can occur before the inner publisher starts, for example when an approved installed edit must first be adopted from its single managed origin. After coordinating one publication owner, explicitly release that exact attempt with the existing [coordinator](../tools/worktree_sync.py):

```text
python tools/run.py worktree_sync release --repo DEVELOPMENT_CHECKOUT --attempt ATTEMPT
```

Release accepts only the recorded `selected owner missing, unadmitted, or conflicting` rejection in `reconciling`, bound to the frozen ready source and selection, with explicit `deployment_started: false` evidence. New coordinator attempts initialize that marker; the ready reconciler durably sets it before entering any possible live mutation and never clears it on retry. Legacy attempts without the marker remain refused by default: an old rejection and an absent inner receipt cannot prove that a later retry never deployed. Release also requires unchanged owned worktree identities, upstreams, HEADs, index and composition, and no inner publisher receipt or unfinished Git operation. Deployed, published, changed or uncertain attempts remain blocked. Release neither deploys nor fetches, resets files, deletes journals, or changes managed baselines.

For a legacy attempt with an absent marker, an explicitly reviewed external execution history may qualify the same release operation with `--qualification RECEIPT`. First coordinate the publication owner, inspect the actual remote and live state, and obtain independent review of complete native execution coverage through a recorded recovery checkpoint, including delegated mutation-capable operations. The terminal original sync output must establish the early rejection; subsequent coverage must exclude a retry or unexplained operation. Current equality, file timestamps and missing receipts are only corroboration. Any later sync or unexplained operation invalidates that coverage, even if current hashes match again. If history remains uncertain, stop with the exact missing evidence. Never insert a retrospective marker or qualify any explicit marker value through this route.

The private operational receipt uses `schema_version: 1`, `kind: reviewed-legacy-predeployment`, the exact original `journal_sha256`, and `binding` with `attempt`, `ready`, `base` and `composed_tree`. Record native `original_sync_command_id` and `checkpoint_command_id`; `review` contains `decision: qualified-predeployment`, `reason`, `reviewer_ref`, `coverage_end` and `no_retry_since_checkpoint`. Its `evidence` maps the six reviewed roles `execution`, `supplement`, `state`, `remote`, `remote_checkpoint` and `checkpoint` to distinct sibling JSON `file` names and their exact `sha256`. Its `live` rows cover every frozen origin destination with `root`, `managed_state_sha256` and an `owners` map from each selected owner to its directory SHA256. Keep native transcripts and private paths outside public source. The existing mechanism fixtures show this record's shape and preservation behavior.

Under the common lock, release verifies those bindings and evidence bytes, rechecks selected installed packages and managed state alongside its normal preflight, and retains the receipt and all six evidence files before changing the active journal. Exact retries use and verify the retained qualification. This records a reviewed decision: shape and hash checks do not authenticate native history, establish semantic completeness, prove the absence of ungoverned writers, or authorize publication. The invoking owner remains responsible for the historical review and continuous no-retry coverage through release.

Under the common publication lock, release retains the original journal byte for byte, renames the integration branch, and moves the entire integration worktree and its marker into `agent-signal-released-ATTEMPT` in the shared Git directory. The completion journal remains there too. An interrupted release blocks publication; repeat the same release command to verify and finish its retained moves. Concurrent edits stop recovery without overwriting them. The released branch and worktree remain available for inspection; the normal ready workflow can create a clean integration lane afterward. Reconcile the approved origin through the existing scoped adoption path before composing a new checked ready commit against that actual baseline. Release does not approve the origin, resolve content conflicts, or transfer an earlier ready receipt to a new baseline.

Release verifies each worktree's Git registration backlink as well as its source. If Git stops inside its own directory move and registration no longer matches the retained path, release keeps the blocking journal. Inspect the physical worktree and its recorded ownership before using Git's native `worktree repair` on that exact owned path; then repeat the exact release command. Release does not repair uncertain registration automatically.

Mechanism tests establish integration, preservation, conflict, lock, and retry behavior against local Git/fleet fixtures. Installed content and remote readback are separate deployment evidence. Neither establishes a model-quality gain, universal host parity, or billed savings.
